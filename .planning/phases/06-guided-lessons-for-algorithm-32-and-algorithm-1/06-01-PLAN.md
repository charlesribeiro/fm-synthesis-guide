<phase_decisions>
Discretion calls locked here so plans 06-02 / 06-03 / 06-04 do not re-litigate them.

- **`LessonId` is a distinct string-slug union, not a reuse of `AlgorithmId`.** Values are
  `'algorithm-32'` and `'algorithm-1'` (RESEARCH Open Question 1's recommendation). A distinct type
  costs nothing now and does not bake "exactly one lesson per algorithm, forever" into the URL
  shape that Phase 11's thirty further lessons inherit.

- **`TryThisParam` is narrower than D-02's literal `keyof OperatorParameters`.** It is
  `'ratio' | 'detune' | 'outputLevel' | 'envelopeLevel'`. `enabled` and `mode` are excluded because
  neither has a meaningful increase/decrease direction (RESEARCH Pitfall 3). `fixedFrequencyHz` is
  excluded for a second reason the research did not reach: it is documented inert while an operator
  is in ratio mode (`operator-parameters.ts` lines 32-37), so a try-this step targeting it would be
  silent — and an inaudible try-this step cannot satisfy D-06's "so the change was actually heard".
  This narrowing is a strict subset of D-02's shape and preserves its intent (structured,
  verifiable data); it does not reduce what any lesson in this phase can express.

- **Completion is a one-way ratchet within a session.** `markComplete` only ever adds; nothing
  removes (RESEARCH Open Question 2). A learner who moves the parameter back after completing
  keeps the completion. Progress is in-memory only and resets on reload — persistence is
  PERSIST-01 (Phase 12), explicitly out of scope (D-07).

- **No file in this phase imports `effect` from `@angular/core`.** The "moved in direction" half of
  D-06 is a pure `computed` comparing live `InstrumentState.operators()` against the lesson's own
  compile-time `startingPatch`; the "and then a note was played" half is an ordinary
  DOM-originated component output event read imperatively inside its handler. Neither half is state
  derivation through a side channel.

- **`SynthEngine` is not widened.** `src/app/core/audio/synth-engine.ts` and
  `web-audio-synth-engine.ts` are untouched by this phase. "A note was played" is a UI fact owned
  by the component that decides whether to call `noteOn`, not an engine-boundary concern
  (RESEARCH Pitfall 2). Writing to `InstrumentState` directly is already picked up by the engine's
  existing constructor effect (`web-audio-synth-engine.ts` lines 152-176), so the try-this control
  needs no engine API at all.

- **The lesson's starting patch is applied by a `LessonDetail` `effect` that tracks the resolved
  lesson from `route.paramMap` and reapplies that lesson's `startingPatch` whenever the id
  changes** (guarded so same-id re-runs do not rewrite live try-this edits). Same-component
  lesson→lesson navigation is covered by the regression test `'reapplies the new lesson starting
  patch when navigating between lesson ids on the same component'`. **Phase 11 note:** adding
  prev/next lesson stepping must keep this route-reuse-safe mechanism (do not regress to a
  one-shot constructor / `route.snapshot` apply), not simply add links against a stale patch.

- **The try-this control is a single range input scoped to the lesson's own target parameter.**
  Not a six-operator editor. Its positions are indices into `tryThisParamValues(targetParam)`, the
  domain-owned ascending ladder of legal values for that parameter, so every value it can write is
  already valid — `InstrumentState.updateOperator`'s `RangeError` guards remain the write path and
  the last line of defence (T-06-03 / T-06-04), never a bypassed one.

- **`playground.spec.ts` is the extraction's regression gate and must not be edited.** Its
  assertions are DOM- and engine-level (`.key`, `[data-note]`, `button.button--primary`, injected
  `SYNTH_ENGINE`, `window` blur, fixture destroy), all of which still resolve when the markup is
  rendered by a child component. Keeping the file byte-identical is a stronger proof of parity than
  any rewritten spec could be (RESEARCH Pitfall 5).
</phase_decisions>

describing the third partial thinning out of the tone while everything else stays put.

`try-this.ts` exports two pure functions with no Angular import and no side effects, following
`derive-role.ts`'s style. `hasMovedTowardTarget(baseline: OperatorParameters, current:
OperatorParameters, tryThis: TryThisStep): boolean` reads `baseline[tryThis.targetParam]` and
`current[tryThis.targetParam]` and returns whether the current value is strictly greater than the
baseline for `'increase'`, strictly less for `'decrease'`. It must compare the specific parameter's
value, never whole `OperatorParameters` objects by reference — `updateOperator` deliberately keeps
untouched operators reference-identical, so a reference comparison would silently never fire.
`tryThisParamValues(param: TryThisParam): readonly number[]` returns the ascending ladder of legal
values for that parameter: `COARSE_RATIOS` for `'ratio'`; every integer from `MIN_DETUNE` to
`MAX_DETUNE` for `'detune'`; every integer from `MIN_OUTPUT_LEVEL` to `MAX_OUTPUT_LEVEL` for
`'outputLevel'`; every integer from `MIN_ENVELOPE_LEVEL` to `MAX_ENVELOPE_LEVEL` for
`'envelopeLevel'`. Read every bound from the exported constants in `operator-parameters.ts`; write
no numeric literal bounds in this file. The function must be total over `TryThisParam` with no
default branch, so adding a parameter to the union is a compile error rather than a silent gap.

**Step 3 — the progress facade (`src/app/state/lesson-progress.ts`).** An
`@Injectable({ providedIn: 'root' })` class named `LessonProgress` mirroring `InstrumentState`'s
shape exactly: a private `_completed` writable signal holding a `ReadonlySet<LessonId>` seeded
empty, exposed as a public readonly `completed` signal via `asReadonly()`. `isComplete(lessonId:
LessonId): boolean` validates via `isLessonId` first and throws a `RangeError` naming
`LESSON_IDS` on an unknown id, exactly as `hasSnapshot` does for snapshot slots, then reads the
set. `markComplete(lessonId: LessonId): void` validates the same way before any write, returns
early when the id is already present so a repeat call keeps the existing set reference, and
otherwise writes a brand-new `Set` built from the previous one plus the id — immutable update, and
a one-way ratchet that never removes. Store nothing but lesson ids: no note numbers, no timestamps,
no engine references, no audio nodes.
