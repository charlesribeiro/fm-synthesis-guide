  <name>Task 1: Blocking human verification — listen to both lessons and walk them as a learner</name>
  <what-built>
Plans 06-01 through 06-03 delivered: the `PlaySurface` component extracted out of `Playground` and
embedded on both lesson pages; the `/learn` index rebuilt from the canonical `LESSONS` dataset with
a worded per-card completion state; `/learn/algorithm-32` and `/learn/algorithm-1` rendering
objective, explanation, embedded routing diagram, try-this control and embedded play surface on one
scrolling page; and a completion check that fires only after the try-this parameter moves in the
stated direction and a note is then played.

Everything mechanical is already proven by automated tests: `playground.spec.ts` still passes
byte-identical, `notePlayed` emits only on a successful key press, the two-condition completion rule
is asserted in both directions, every rejected lesson address renders not-found without throwing,
and every lesson row's starting patch passes the same validators `InstrumentState` enforces. What no
test can reach is whether it sounds and feels right.
  </what-built>
  <how-to-verify>
Run `npm start` and open the app in a real browser (not the test runner). Work through all five
checks and report each one individually.

1. **Extraction parity, by ear.** Open `/playground`, enable audio, and play a few notes with the
   mouse and with the computer keyboard. Then open `/learn/algorithm-1`, enable audio there, and
   play the same notes. Listen for: any click or pop at note start or release that was not there
   before; any note that keeps sounding after you let go; any key that stops responding. Also try
   right-clicking a key, holding a key and pressing Tab, and switching to another window mid-note,
   on both pages. Expected: identical behaviour in both places, no stuck note anywhere.

2. **Completion timing, as a first-time learner.** Open `/learn/algorithm-32` fresh. Before touching
   anything, confirm it reads as not started. Play a note without touching the try-this control —
   it must still read as not started. Reload, move the try-this control as the instruction says but
   play no note — still not started. Now move the control and then play a note — it must flip to
   complete. Repeat the whole sequence on `/learn/algorithm-1`. Expected: complete only on the
   second half of the pair, never earlier, never never.

3. **The lesson actually teaches what it claims.** On `/learn/algorithm-32`, lower operator 3's
   output level while holding notes and confirm you hear one component of the tone thin out while
   the rest stays. On `/learn/algorithm-1`, raise the target operator's ratio and confirm the
   tower voice gets brighter while the pair voice is unchanged. Expected: the audible effect matches
   the "what you should hear" text. If it does not, the lesson's starting patch or its try-this
   target needs tuning — say what you heard instead.

4. **Keyboard only.** Put the mouse away. From `/learn`, Tab to a lesson card, activate it, Tab
   through the page to the try-this control, change it with the arrow keys, Tab to a key and play a
   note with Space or Enter, and reach the completion state. Expected: every step reachable, focus
   always visible, nothing trapping focus.

5. **Colour independence and reduced motion.** Confirm the completion state on both the lesson page
   and the `/learn` cards is readable as words, not just a colour or a tick. Then turn on your OS
   "reduce motion" setting, reload, and complete a lesson again. Expected: state changes appear
   instantly with no animation.

Report per check: pass, or what you saw/heard instead. If check 3 needs a different starting patch
or a different try-this target, say which lesson and what you would change.
  </how-to-verify>
  <resume-signal>Type "approved" if all five checks pass, or list the failing check numbers with what you observed.</resume-signal>
</task>
