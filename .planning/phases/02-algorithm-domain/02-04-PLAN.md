## The routing table disagrees with itself — read this before entering any row

RESEARCH.md § Routing Reference Table has two columns that encode the same fact by different
routes: a **Carriers** column and a **Modulation edges** column. Under D-05 carriers are *derived*
from edges, so the two must agree. **They do not agree for 14 of the 32 rows.** This was computed
during planning by applying D-05's rule to the table's own edge lists; it is not a hypothetical.

The two columns do not carry equal weight, and RESEARCH.md says so itself in its confidence key
and metadata: carrier sets and feedback operators are **HIGH** confidence, triangulated across
three independent sources with a documented and resolved disagreement; exact intermediate edges
are **MEDIUM** for roughly 24 rows, reconstructed from the higher-modulates-lower structural rule
plus pattern matching rather than re-derived from a second source.

**Therefore the Carriers column is authoritative and the edge list is what gets repaired.**

### Reconciliation rule (binding)

For each of the 14 ledger rows, repair the **edge list**, never the carrier set, subject to four
constraints in priority order:

1. `deriveCarriers()` on the repaired row must equal the researched carrier set exactly.
2. Every non-self-loop edge keeps `from > to`.
3. The feedback operator stays exactly as the table states it.
4. The repair is the **minimal** edit satisfying 1 through 3 — keep as many of the stated edges
   as possible, and add or remove as few as possible. Do not restructure a row further than the
   constraints force.

Where constraints 1 through 3 do not determine a unique repair, choose the option preserving the
largest number of the originally stated edges, and mark the row `ambiguous` in the SUMMARY. Where
a row would need more than one invented edge to satisfy constraint 1, stop rather than guess:
enter the row with the edges the constraints do force, mark it `unresolved` in the SUMMARY, and
leave it for the Plan 02-05 reviewer. Fabricating topology to make a test pass is the one failure
mode this whole plan exists to prevent.

**An `unresolved` row is an explicit, tracked exception, not a silent pass.** Constraint 1 requires
`deriveCarriers()` to reproduce the researched carrier set — an `unresolved` row is by definition a
row where that constraint is *not yet* satisfied. Task 2's per-row cross-check must not claim such a
row's carriers match `EXPECTED_CARRIERS`, and no SUMMARY, phase-verification, or sign-off document
may report the dataset as "fully verified" or "no unresolved rows" while an `unresolved` row remains.
Either the row is resolved (its edges satisfy constraint 1, and it changes status to `repaired` or
`ambiguous`) before such a claim is made, or the claim is scoped to explicitly exclude it by id.

Record every ledger row in the SUMMARY as `id: stated-edges -> entered-edges` with the constraint
that forced each change and a status of `repaired`, `ambiguous`, or `unresolved`.
