<objective>
Prove every one of the 32 algorithms routes correctly, and that no algorithm can
produce an unbounded or non-finite sample at maximum feedback.

Purpose: A single shared implementation tested against itself proves nothing.
D-10 requires a second, separately-authored phase-modulation evaluator so a
translation bug in the router's graph-to-render step fails a named row instead of
shipping. D-11 requires the bounded-output proof to run for the full set rather
than only the rows that look risky.

Output: An independent recursive reference evaluator, and a 32-row cross-check
plus bounded-output sweep that both run in plain Vitest with no browser.
</objective>

  <behavior>
    - For an algorithm with a single carrier and no modulation edges, `evaluateAlgorithmReference` returns `carrierAmplitude * outputGain * sin(2*pi*f*i/sampleRate)` at each sample index `i`, bounded.
    - For a two-operator chain (one modulator into one carrier, no feedback), the carrier's sample at index `i` is `sin(2*pi*fc*i/sampleRate + index_m * sin(2*pi*fm*i/sampleRate))`.
    - For an operator with a self-loop, the self term at sample `i` uses the value that operator produced at sample `i-1`, and is zero at `i=0`.
    - An operator with two incoming edges receives the sum of both scaled modulator samples.
    - An operator with both incoming edges and a self-loop receives both contributions in the same sample's phase argument.
    - Carriers are exactly the operators with no outgoing edge to a *different* operator; a self-loop alone never disqualifies an operator from being a carrier.
    - Every returned sample is finite and inside the bound.
  </behavior>

  <action>
Create `src/app/domain/dx7/dsp/reference-evaluator.ts` as a deliberately second, structurally different phase-modulation implementation, written for D-10's cross-check and imported only by test files.

Open with the domain-purity header comment convention every sibling in `dsp/` uses, and state plainly why this module exists and what it may not do: it is the independent side of a two-implementation correctness proof, so it must import nothing from `graph-router.ts`, nothing from the canonical role-derivation module (`derive-role.ts`), and nothing from the connection planner (`patch-plan.ts`). Those helpers are already proven in isolation by Phase 2's own suites; this module's job is to catch a bug in the router's own graph-to-render translation, and calling into the same shared code would let a shared bug pass both sides. Also state that it is test-only, that it may recompute freely because the no-allocation-in-the-render-loop rule targets the audio render loop and not a Vitest-only evaluator, and that it is an original implementation never derived from any DX7 or Dexed source.

Export `interface ReferenceEvaluationInput` carrying: `sampleRate`, `blockSize`, `operatorFrequenciesHz` and `modulationIndices` and `carrierAmplitudes` each as a `Readonly<Record<OperatorId, number>>`, `feedbackIndex`, and `outputGain`. Export `evaluateAlgorithmReference(algorithm: AlgorithmDefinition, input: ReferenceEvaluationInput): Float32Array`.

Structure it recursively and per-sample, which is the shape that makes it genuinely different from the router's iterative per-block descending sweep. Inside the function, define small local helpers that read `algorithm.edges` directly: one that reports whether an operator has an edge to a *different* operator (its negation is the carrier test — a self-loop alone must never disqualify a carrier, which is the exact subtlety `algorithms.ts` row 32 depends on), one that lists an operator's incoming edges from *other* operators, and one that reports whether an operator has a self-loop. Keep a per-operator feedback-history record initialised to zero for all six ids.

A `sampleAt(id, sampleIndex)` inner function memoizes each operator's computed sample once per sample index and returns the cached value on repeated fan-out evaluations (an operator that feeds two downstream targets must not be recomputed, or its self-loop history would advance twice in the same sample). On a cache miss it computes the operator's phase as `((frequency * sampleIndex) / sampleRate) % 1`, sums `sampleAt(modulatorId, sampleIndex) * modulationIndices[modulatorId]` over every incoming modulator, adds `feedbackIndex * feedbackHistory[id]` when that operator has a self-loop (feedback reads only the prior sample's history), evaluates `Math.sin(2 * Math.PI * phase + modulation)`, stores that value in the per-sample cache *before* writing it into `feedbackHistory[id]` when it has a self-loop, and returns it. Walk sample indices in ascending order in the outer loop so the feedback history is always the previous sample's value.

One numerical detail is load-bearing and must be implemented and commented: apply `Math.fround` to each operator's returned sample and to each accumulated modulation total, because the router stores every intermediate block in a `Float32Array` and a five-deep modulation chain amplifies a single-precision rounding difference by roughly the product of the chain's modulation indices — enough to break a tight tolerance for reasons that are storage precision, not a routing bug. This mirrors the router's *storage precision* only; it is not shared code and does not weaken the independence of the derivation.

For each sample index, sum `sampleAt(id, i) * carrierAmplitudes[id]` over the carriers, multiply by `outputGain`, apply the same two-sided hard bound the router applies, and write into the output `Float32Array`.

Create `reference-evaluator.spec.ts` covering the evaluator on its own small hand-built fixtures — not against the router, which is Task 2's job. Assert each behaviour listed in this task's behavior block using inline `AlgorithmDefinition`-shaped fixtures with hand-computed closed-form expectations, following `operator.spec.ts`'s existing analytical-reference convention. Include the self-loop-does-not-disqualify-a-carrier case explicitly, and a case where an operator has both incoming edges and a self-loop.
  </action>

Create `src/app/domain/dx7/dsp/algorithm-routing.spec.ts` as the D-10 and D-11 proof.

Build one shared fixture helper both implementations receive identically. It must make every operator distinguishable, otherwise a routing bug that swaps two operators, or drops one, can cancel out and pass. Give operator id `N` a distinct coarse ratio (use `N` itself, which is a member of `COARSE_RATIOS`), a distinct `outputLevel` spread across the DX7 range rather than the uniform default, and a distinct `detune` inside the legal bounds; keep `mode` at `'ratio'` and `enabled` at `true` for the cross-check fixture. Derive the two implementations' inputs from that same parameter set: for the router, apply `buildRoutingConfig(algorithm)`, the parameter set, the feedback level and the note frequency through the router's own setters; for the reference, compute the per-operator frequencies with `operatorFrequencyHz`, the per-operator modulation indices as `outputLevelToModulationDepthHz(outputLevel, frequency) / frequency`, the per-operator carrier amplitudes with `outputLevelToAmplitude`, the feedback index as `feedbackLevelToDepthHz(level, feedbackOperatorFrequency) / feedbackOperatorFrequency`, and the output gain as `MASTER_GAIN`. Deriving both sides' *scalar inputs* from the same conversion functions is correct and required — those functions are Phase 5 code already proven in isolation, and D-15/D-16 mandate their reuse. What must stay independent is the graph traversal and the per-sample evaluation, which is exactly what this cross-check exercises.

Declare a spec-local `CROSS_CHECK_DECIMAL_PLACES` constant, initially 6, matching the Phase 7 analytical-match precedent. Use `describe.each(ALGORITHMS)` with a title carrying the row's id and name so a failure names the algorithm. Per row, add one case asserting the router's block matches the reference block at every sample index within that tolerance, and a second case rendering at feedback level 7 with every operator at the maximum output level and asserting every sample is finite, at least the lower bound, and at most the upper bound. Render more than one block in the feedback sweep so the feedback recurrence has actually accumulated state, not just its first zero-history sample.

If any row fails at 6 decimal places once the reference's single-precision mirroring is in place, do not silently loosen the constant. Instead: measure and record the worst absolute deviation across all 32 rows, set `CROSS_CHECK_DECIMAL_PLACES` to the tightest value that passes every row, add an assertion that the worst observed absolute deviation stays below one thousandth (below that threshold the difference is single-precision noise; above it, it is a routing bug and must be fixed rather than tolerated), and record both numbers plus the reasoning in the plan summary as a deviation. Never weaken the tolerance to accommodate a difference larger than that threshold.

Add a final `describe` block covering degenerate configs the validated dataset can never produce but the message boundary theoretically could: a config with an empty carrier list must render an all-zero block rather than non-finite samples, and a config whose only connection is the feedback self-loop must leave every other operator unmodulated. These are defensive assertions at the router's own API, below the message validation layer.

Add one comment near the feedback sweep recording the verified dataset fact that all 32 rows already declare a feedback self-loop, so D-11's "not only the rows with declared feedback" framing is a design principle this sweep keeps rather than a distinction this dataset currently exhibits.
