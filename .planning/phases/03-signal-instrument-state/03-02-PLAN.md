<design_decisions>
Decisions this plan makes inside CONTEXT.md's "Claude's Discretion" area:

**Snapshots store a patch value, not a deep clone.**
Plan 01 makes every command produce a new patch object rather than mutating the previous one, so a
captured reference can never be changed out from under the slot. Capture is therefore a reference
store, and it is exact by construction. This is only sound because of the immutability contract in
plan 01 — the isolation tests in Task 2 exist to prove that coupling still holds, so a future
regression to in-place mutation fails here loudly rather than silently corrupting snapshots.

**`recallSnapshot` returns a boolean; `reset` returns void.**
Recall can legitimately fail (empty slot); reset cannot. See the flagged assumption in frontmatter
for the reasoning behind the empty-slot no-op.

**Slot identifiers are a restricted union type.**
`type SnapshotSlot = 'a' | 'b'` with a frozen `SNAPSHOT_SLOTS` array, mirroring the
`OperatorId`/`OPERATOR_IDS` and `TeachingTag`/`TEACHING_TAGS` convention already used across the
domain layer. This is what makes "exactly two slots" a compile-time fact rather than a convention a
future phase could quietly widen.
</design_decisions>

  <action>
In `src/app/state/instrument-state.ts`, export `type SnapshotSlot = 'a' | 'b'`, a frozen
`SNAPSHOT_SLOTS: readonly SnapshotSlot[]` holding 'a' and 'b', and
`type SnapshotSlots = Readonly<Record<SnapshotSlot, InstrumentPatch | null>>`. Use the
`Object.freeze` array pattern already used for `TEACHING_TAGS` and the restricted-union pattern
used for `OperatorId`. Null is how an uncaptured slot is represented — do not add a parallel
`hasBeenCaptured` boolean field that could disagree with it.

Add a second private writable signal holding `SnapshotSlots`, initialised with null in both slots,
exposed publicly as `readonly snapshots: Signal<SnapshotSlots>` via `.asReadonly()`. Keep it
strictly separate from the patch signal: no command other than `captureSnapshot` may write it, and
in particular `reset` must not (D-04).

Add `captureSnapshot(slot: SnapshotSlot): void` — read the current patch signal value and store
that value into the given slot with an immutable spread of the snapshots record. No cloning: plan
01 guarantees every command produces a new patch object rather than mutating the previous one, so
the stored value cannot change afterwards. State that guarantee, and its dependence on plan 01's
immutability contract, in the method's doc comment. Capturing into an occupied slot overwrites it.

Add `recallSnapshot(slot: SnapshotSlot): boolean` — read the slot; when it is null, change nothing
and return false; otherwise set the patch signal to the stored patch and return true. Recall does
not clear or alter the slot, so the same snapshot can be recalled repeatedly.

Add `hasSnapshot(slot: SnapshotSlot): boolean` reading the snapshots signal — this is the read a
future recall button uses to decide whether it is enabled, and it stays reactive because it reads a
signal internally.

Add `reset(): void` — set the patch signal to `DEFAULT_PATCH` and touch nothing else. Document in
its doc comment that reset is a third action independent of A and B per D-04: it always restores
the fixed default patch regardless of what the slots hold, and never overwrites them. Because it
assigns the very same `DEFAULT_PATCH` constant that seeds the facade's initial state, post-reset
state is identical to first-load state by construction rather than by a parallel definition that
could drift.

Extend the class doc comment to record D-05: snapshots and reset are in-memory only for this phase,
with no persistence across a page reload; versioned storage and import/export are PERSIST-01's job
in Phase 12, and an ad hoc version added here would have to be removed.

Add every test from `<behavior>` to `instrument-state.spec.ts`, keeping all existing tests intact.
Follow the existing convention of a one-line comment on each test citing the decision id or

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Angular component/service -> `InstrumentState` snapshot commands | The only input path. In-process, statically typed, slot identifiers restricted to a two-member union. No network, no storage, no deserialization. |

Same posture as plan 01: this phase has no external attack surface. Snapshots are in-memory
JavaScript objects (D-05). Authentication, session management, XSS, CSRF, and injection categories
do not apply to an in-memory state facade with no I/O and are deliberately omitted rather than
padded in. ASVS L1, block-on-high: nothing here reaches high.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-05 | Tampering | Captured snapshot values in the snapshots signal | medium | mitigate | A snapshot that shares mutable structure with live state would silently drift from what the user captured, making the A/B comparison lie — the pedagogical core of the feature. Mitigated by plan 01's immutable-update contract plus the Task 2 isolation tests that fail if any command starts mutating a patch in place. |
