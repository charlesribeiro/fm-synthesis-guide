**1. `tools-panel.ts`.**

A standalone component with the selector `app-tools-panel`, on-push change detection, and template and style URLs, following `play-surface.ts`'s component-shell shape exactly. Inject `InstrumentState` directly — it is root-provided, so no new provider is needed anywhere.

Expose two `computed` wrappers over the facade's slot predicates, one per slot, and derive from each a worded label for its recall button and a worded slot-state line. These wrappers are the only derived state the component may hold: do not mirror the snapshots signal, do not cache patches, and do not track which slot was recalled most recently. The facade has no notion of a currently-active slot, which is exactly why D-09 rejected a toggle switch; inventing that notion here would recreate the derived state that decision declined to build.

Expose six handler methods, each a single call into the facade and nothing else: capture for each slot, recall for each slot, reset, and randomize. After each call set a component-local status message signal describing what happened in words. For recall, use the boolean the facade returns to distinguish a real recall from a no-op on an uncaptured slot, so the message can never claim a recall that did not happen even though the button is disabled in that state.

Document at the top of the class that this component deliberately contains no state logic: the capture, recall, has-snapshot and reset commands were completed and tested in Phase 3, and the randomize command in plan 10-03, so anything here beyond dispatching to them and describing the result in words is scope this component should not own.

**2. `tools-panel.html`.**

A section with an accessible heading naming it as the comparison and randomization tools. Group the four snapshot buttons and their two worded slot-state lines together, then Reset, then Randomize, each a real button element with a plain visible text label. The recall buttons carry the worded label from the computed wrapper so that an empty slot is stated in the label text itself rather than implied by the disabled attribute, and carry the disabled binding from the same wrapper. Render the two slot-state lines as plain text sentences. Add a status live region for the last-action message, following the same role the play surface already uses for its audio status.

Give the Randomize button a short adjacent line of explanatory text stating that randomizing nudges the operators and feedback from the current sound and never changes the selected algorithm, and that capturing to a slot first is the way to keep the current sound. That line is the user-facing form of D-12 and D-14 and is what makes the absence of an undo an understood design rather than a missing feature.

**3. `tools-panel.scss`.**

Follow `play-surface.scss`'s posture: an embedded region with no page-layout mixin, replicating the existing button rule bodies rather than assuming a global button style, spacing and colours from the existing custom properties only, a visible focus indicator, and a disabled appearance that changes more than hue. Add nothing that animates.

**4. `tools-panel.spec.ts`.**

Cover every case in this task's behavior block. Query buttons by their accessible text rather than by position, so a layout change does not silently retarget an assertion.

For the no-implicit-randomize case, spy on the randomize command, then create the component, activate all five other buttons in turn, and destroy the component, asserting the spy was never called; then activate Randomize and assert it was called exactly once. For the state-carried-in-text case, assert that the rendered text of the panel contains a worded statement of each slot's state both before and after a capture, and that the two statements differ.


Navigate to `/playground` and press Enable audio. Work through all ten checks and

**Check 1 — the oscilloscope is the sound.** Hold a note. The trace must move
continuously while the note sounds and must return to a flat line shortly after
release. Hold a low note and then a high note: the visible cycle spacing must
change with pitch. If the trace moves when nothing is sounding, or does not
change with pitch, stop and report — the display would be showing something other
than the live tap.

**Check 2 — the spectrum reads as harmonic content.** Hold a note and watch the
bars. Play an octave higher: the active bars must shift right by a consistent
visual distance, because the axis is logarithmic. On an algorithm with an audible
modulator, the sideband bars either side of the fundamental must be visible as
separate columns rather than smeared into one.

**Check 3 — bar heights are readable (RESEARCH Assumption A3).** Judge whether
the bars use a useful part of the available height at normal playing level. If
they are nearly invisible or pinned at full height for every note, report that —
it means the analyser's decibel window needs tuning against this project's master
gain, which is a two-constant change and not a structural one.

**Check 4 — the axis labels are correct and legible.** The three tick labels must
read 100 Hz, 1 kHz and 10 kHz, be readable at normal zoom, and sit at plausible
positions relative to the bars a played note lights up.

**Check 5 — A/B capture and recall.** Capture A. Change the sound noticeably —
Randomize is the quickest way. Capture B. Recall A, then Recall B, then A again.
Each recall must restore the corresponding sound exactly, and both recall buttons
must have been disabled with wording saying the slot was empty before their first
capture.

**Check 6 — mid-note recall is click-free (D-11).** Hold a note and, while it is
still sounding, press Recall A and then Recall B. Listen for a click, pop or
dropout at each swap. This is a spot-check of Phase 9's envelope continuity, not
a re-verification of it — report any click you hear.

**Check 7 — Randomize is a nudge, not a reroll.** Press Randomize five or six
times in a row while holding notes between presses. Each result must be audibly
different from the last but recognisably related to it, and none may be silent,
distorted, or painfully loud. Confirm that the selected algorithm never changes
across any of the presses.

**Check 8 — Reset keeps the slots.** Press Reset. The sound must return to the
default patch, and both recall buttons must still be enabled with the same slot
wording as before the reset. Recall A and confirm the captured sound comes back.

**Check 9 — keyboard only.** Without touching the pointer, tab through the page.
All six tools buttons must be reachable in a sensible order, each must show a
clearly visible focus indicator, each must activate with Enter or Space, and the
disabled recall buttons must not trap focus. Confirm that the tools panel's
keyboard use does not interfere with the play surface's own note keys.

**Check 10 — reduced motion and honest copy.** Turn on the operating system's
reduce-motion setting and reload. The two displays must still show live data but
visibly update at a slower rate rather than freezing or animating at full speed.
Then read the panel's caption and descriptions and confirm nothing on the page
claims this is a bit-accurate or hardware-accurate DX7 analysis.

Report each check as pass or fail with a short note. On any failure, describe what
you saw or heard rather than proposing a fix.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User activation → state command | Six controls are the only path from a click to a patch mutation; an implicit path would be a mutation the user never asked for. |
| Facade state → rendered availability | Slot availability is derived for display; a derived copy that drifts from the facade would offer a recall of a slot that holds nothing. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-16 | Tampering | Randomization triggered implicitly by a lifecycle hook or another control | high | mitigate | `randomize` is called from exactly one click handler; a named test asserts zero calls across creation, all five other activations and destruction. There is no undo beyond the slots, so an implicit call is an unrecoverable, silent data loss for the learner's in-progress patch. |
| T-10-17 | Tampering | Reset clearing or invalidating the captured slots | medium | mitigate | Reset dispatches only to the facade's `reset`, which by construction assigns the default patch and never touches the snapshots signal; pinned by a capture-then-reset-then-recall test in task 1. |
| T-10-18 | Spoofing | A recall button offering a slot that holds nothing | medium | mitigate | Both the disabled binding and the worded label derive from the same `computed` over `hasSnapshot`, so they cannot disagree; the handler additionally uses `recallSnapshot`'s boolean return so the status message can never claim a recall that did not occur. |
| T-10-19 | Information Disclosure | — | low | accept | This panel reads and writes only in-memory instrument state in the user's own browser; nothing is persisted, transmitted or shared, so there is no disclosure surface to control. |
| T-10-20 | Denial of Service | A control activated while audio is suspended or unavailable | low | accept | Every control acts on `InstrumentState`, which has no dependency on the audio graph; the commands succeed and the new patch is applied when audio later becomes ready. No gating is added, matching D-11's no-safety-gating decision. |
| T-10-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs zero packages — it is component markup and handlers over facades that already exist. |
