# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope:** the Playground play surface (D-06) — the "Enable audio" gesture gate (D-09), the
12-key one-octave on-screen/computer keyboard (D-05/D-07), and the persistent approximation
label (D-08). No new route. Extends `src/app/features/playground/` in place, replacing its
placeholder `.status` block and `feature-list` bullet for keyboard input.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — Angular 22 standalone project, shadcn is React/Next/Vite-specific and does not apply |
| Preset | not applicable |
| Component library | none — hand-rolled semantic HTML + SCSS custom-property tokens (established Phase 1, `src/styles/_tokens.scss`) |
| Icon library | none introduced this phase. If a status glyph is needed for the gate (e.g. a small speaker/mute icon), use inline SVG with a `<title>`, matching the accessible-SVG pattern already established in `algorithm-diagram.html` (Phase 4) — never an icon font, never the sole indicator of state (text label is always present alongside) |
| Font | `var(--font-sans)` → `'Inter', system-ui, ...` (existing project-wide token, unchanged) |

This phase introduces **no new design tokens**. Every value below is either an existing token
from `src/styles/_tokens.scss` or a phase-scoped exception documented as such.

**Visual focal point.** The Playground screen has exactly one primary visual anchor at a time,
switching with `status()`:

- While `status()` is `'suspended'` / `'enabling'` / `'error'` / `'unavailable'`, the "Enable
  audio" gate panel (accent-colored CTA + supporting copy) is the focal point. The keyboard is
  present but visually inert (see Color's non-color-only inert-state requirement) and is not
  competing for attention.
- Once `status() === 'ready'`, the gate panel is removed from the DOM (Copywriting Contract),
  and the 12-key keyboard becomes the sole focal point — it is the only interactive element
  left above the persistent approximation label, which stays visually secondary (Label-weight
  text, no accent color) throughout both states.

## Spacing Scale

Declared values from the checker's standard set (existing project scale, canonical steps only —
reuse verbatim, do not invent new spacing tokens this phase):

| Token | Value | Usage this phase |
|-------|-------|-------|
| `--space-1` | 4px | Gap between adjacent on-screen keys |
| `--space-2` | 8px | Padding inside the approximation badge; gap between gate button and its status line |
| `--space-4` | 16px | Default gap between gate block, keyboard block, and approximation label block |
| `--space-6` | 24px | Padding around the keyboard container panel |
| `--space-8` | 32px | Page-level block padding (`layout.page` mixin, unchanged) |
| `--space-12` | 48px | Not used this phase |

Exceptions:

- **`--space-3` (12px), used for "Enable audio" button horizontal padding and status/error box
  padding.** 12px is not one of the checker's seven canonical steps (4, 8, 16, 24, 32, 48, 64),
  so it is called out here explicitly rather than presented as a standard value. It is not a
  token invented for this phase: `--space-3: 0.75rem` is defined in `src/styles/_tokens.scss`
  (Phase 1) and is already the established horizontal-padding value for every button and
  status/note box in the codebase — `app.scss` (nav actions), `home.scss`
  (`.button--primary`), `learn.scss`, `algorithms.scss`, `algorithm-detail.scss`
  (`.review-note`), and the existing `playground.scss` itself all use `var(--space-3)` for this
  exact purpose. Rationale for keeping it rather than substituting `--space-2`/8px or
  `--space-4`/16px: 8px reads as visually cramped against this project's 16px body/button text
  (already true of the existing `.button--primary`), and 16px would make the "Enable audio"
  button and the status/error boxes inconsistent in proportion with every other button and note
  box already shipped in the app. Using `--space-2` or `--space-4` here would create a new
  visual inconsistency to fix a spec-table categorization technicality, not a real design flaw.
  This exception is scoped to horizontal button padding and status/error box padding only — no
  other spacing in this phase uses `--space-3`.
- **Minimum touch target 44×44px** for every on-screen key, overriding the visual key width
  where the two conflict. On narrow viewports the 12-key row scrolls horizontally
  (`overflow-x: auto`) rather than shrinking keys below 44px — see UI Considerations "overflow"
  row. This mirrors the existing WCAG-AA-first posture already documented in `_tokens.scss`'s
  header comment.
- **Key gap is 4px (`--space-1`), not 8px**, deliberately tighter than the default inter-element
  spacing — piano-style keyboards read as one contiguous instrument, not a list of discrete
  buttons; the 44px touch-target floor still applies per key.

Role assignment for this phase's elements:

- **Body (16/400/1.5):** gate supporting copy ("Audio is off. Enable audio to play notes..."),

  small size keeps these legible without relying on color to stand out (non-color-only rule).
- **Heading (28/600/1.2):** unchanged `<h1>Playground</h1>`, no change this phase.

## Color

60/30/10 split reuses the existing dark-surface palette verbatim — no new hex values this
phase.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-bg` `#0b0d10` | Page background |
| Secondary (30%) | `--color-surface` `#14171c` / `--color-surface-raised` `#1b1f27` | Gate panel background, keyboard container panel, approximation badge background, unpressed key surface |
| Accent (10%) | `--color-accent` `#5eb1ff` (hover: `--color-accent-strong` `#9ed4ff`) | Reserved for exactly two elements this phase, listed below |
| Destructive | `--color-danger` `#ef6a6a` | Not used this phase — no destructive action exists in this phase's scope (see Copywriting Contract) |

**Accent reserved for:**

1. The "Enable audio" primary CTA button background/border (matches the existing
   `.button--primary` pattern from `home.scss` — reuse that class, do not invent a new button
   style).
2. The pressed/active visual state of an on-screen key while its note is sounding.

**Non-color-only requirement (CLAUDE.md) for the pressed key state:** accent color alone never
communicates "this key is sounding." Pair it with a non-color cue: an inset `box-shadow` +
`transform: translateY(1px)` (physical "pressed" depression) and `aria-pressed="true"`. Respect
reduced motion — the translate is a static offset, not an animated transition, when
`prefers-reduced-motion: reduce` is set (existing global rule in `_tokens.scss` already zeroes
transition durations).

**Non-color-only requirement for the inert (pre-`'ready'`) keyboard state:** do not merely dim
via opacity. Pair reduced opacity (~0.4) with `aria-disabled="true"`, `tabindex="-1"` (removed
from tab order), and `cursor: not-allowed` — three independent, non-color signals that the
keyboard is not yet playable. Every key also uses native `disabled` (or an early return in every
pointer/keyboard handler) whenever `status()` is not `'ready'`, so neither pointer activation nor
Space/Enter/document-keyboard paths can invoke `noteOn`. Spec coverage must assert that pre-ready
pointerdown and keyboard activation never call `noteOn`.

**`--color-warning` (`#f2b84b`)** — reused (not newly introduced) for the border of the
error/unavailable status box, mirroring the existing `.review-note` pattern in
`algorithm-detail.scss`. Not part of the 60/30/10 split; it is the existing project convention
for a non-error-but-attention-worthy message box.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | **"Enable audio"** — exact label, never varies (D-09). Disabled + relabeled "Enabling…" only while `initialize()` is in flight. |
| Empty state heading | Not applicable this phase — no data-driven list/collection exists (the 12-key keyboard is a fixed layout per D-07, never empty) |
| Empty state body | Not applicable this phase (see above) |
| Error state | **"Audio failed to start. Enable audio to try again."** — problem + next step, shown inline above the (still-present, re-enabled) "Enable audio" button when `status() === 'error'` |
| Destructive confirmation | None this phase — no destructive action is in scope (master volume, algorithm reset UI, and octave-shift are all explicitly deferred per CONTEXT.md's Deferred Ideas) |

Additional phase-specific copy (D-08/D-09 exact wording, locked — not "e.g." placeholders):

| Element | Copy |
|---------|------|
| Approximation label (persistent, D-08) | **"Educational approximation — not a bit-accurate DX7 emulation"** — uses "approximation"/"not... emulation," never "emulates," "accurate," or "authentic" unqualified (Pitfall 7 guardrail from 05-RESEARCH.md) |
| Suspended-state supporting copy (D-09) | **"Audio is off. Enable audio to play notes on the keyboard below."** |
| Unavailable-state message | **"Your browser doesn't support Web Audio, so you can't hear sound here. Everything else on this page still works."** — honest, distinct from the error state, does not offer a retry action (retrying cannot succeed) |
| `'ready'` state | Gate panel (button + supporting copy) is removed from the DOM/hidden once `status() === 'ready'`; only the keyboard and the persistent approximation label remain visible |

## UI Considerations

Applicable state considerations resolved: 5 covered, 1 backstop, 0 unresolved (plus 6 categories
explicitly dismissed with reasons below — a fixed, non-data-driven keyboard is exempt from most
of the taxonomy).

**Elements classified:**

| id | text | element kind(s) |
|----|------|-----------------|
| gate | "Enable audio" gesture gate (button + status copy), covers suspended/enabling/ready/error/unavailable | interactive-control |
| keyboard | 12-key fixed one-octave on-screen keyboard, each key also computer-keyboard-mappable | list-collection, interactive-control |
| badge | Persistent approximation label | static-content |

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| loading | gate | ✅ covered | While `initialize()` is in flight, the button is disabled and relabeled "Enabling…"; prevents a double-invocation retriggering `new AudioContext()` mid-gesture |
| error | gate | ✅ covered | `status() === 'error'` renders "Audio failed to start. Enable audio to try again." above a re-enabled "Enable audio" button (Copywriting Contract) |
| error | gate (unavailable) | ✅ covered | `status() === 'unavailable'` renders the distinct honest message with no retry affordance (Copywriting Contract); rest of the app remains fully navigable |
| populated | keyboard | ✅ covered | All 12 keys render unconditionally as soon as the component mounts; visual enabled/inert state is driven entirely by gate status, not by conditional rendering of the keys themselves |
| overflow | badge | ✅ covered | Fixed short copy string wraps to a second line on narrow viewports rather than being clipped or truncated — full text always readable |
| overflow | keyboard | 🧪 backstop | The 12-key row must remain reachable via horizontal scroll (`overflow-x: auto`) on viewports too narrow to fit all 12 keys at the 44px touch-target floor, never shrinking a key below 44px and never wrapping to a second row — verify with a narrow-viewport manual/backstop check, since automated layout width assertions are brittle |
| empty | keyboard | dismissed | Fixed 12-key range per D-07, never data-driven by algorithm or patch state — no algorithm can produce zero playable keys, so no empty state is representable |
| loading | keyboard | dismissed | The keyboard has no independent async load; its enabled/inert state is entirely derived from the gate's status (covered under the `gate` rows above), not a separate loading state of its own |
| error | keyboard | dismissed | The keyboard as a collection cannot independently fail to load — any failure is a gate-level `'error'`/`'unavailable'` status, already covered above |
| zero-one-many | keyboard | dismissed | Always exactly 12 keys, no zero/one/many variability to design copy or spacing for |
| long-text | keyboard | dismissed | Each key's printed labels are 1–2 characters ("C4", "A") — fixed, short, never user-generated; no overflow risk |
| long-text | badge | dismissed | Fixed, locked copy string (Copywriting Contract) — not user-generated or dynamic, so no long-text variability exists |
