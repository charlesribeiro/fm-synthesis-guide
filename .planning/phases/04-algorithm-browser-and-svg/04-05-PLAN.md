<design_decisions>
**A separate sweep file, not an extension of the fixture spec.**
`algorithm-diagram.spec.ts` (Plan 01) is the readable contract on two well-understood fixtures: it
is where a maintainer goes to learn what the component guarantees. The 32-row sweep is a different
kind of test — a dataset-wide invariant with accumulate-and-report failure handling. Keeping them in
separate files means neither is diluted, and it keeps this plan's file set disjoint from every other
plan in the phase.

**Every expectation is computed, never transcribed.**
The sweep derives its expected sentences and counts from `ALGORITHMS` and the existing derivation
helpers at test time. Phase 2 already demonstrated what a transcribed second copy costs: the
Algorithm 26/27 correction had to be applied in two places, and the cross-check tables in
`algorithms.spec.ts` exist precisely because a transcription slip must fail a named test rather than
ship silently. The one thing that sweep style must not become is a third copy.

**One checkpoint for the phase, not one per plan.**
The layout legibility review, the keyboard walkthrough and the screen-reader spot check all need the
same running application and the same 32 pages open. Splitting them across plans would ask the
developer to boot the app three times and would fragment the record.
</design_decisions>

  <action>
Create `algorithm-diagram.coverage.spec.ts` as a non-routed component suite using the same `TestBed`
setup as Plan 01's fixture spec. For each id from 1 to 32, build the view model with
`buildDiagramViewModelForId`, create a component fixture, set the `viewModel` input, await
stability, then query the rendered DOM. Accumulate every mismatch as an entry carrying the algorithm
id and a short reason, and assert at the end of each `it` that the accumulated list is empty, so a
failure names every algorithm that broke and why.

Assert these groups, one `it` each:

Description completeness across the dataset. For each algorithm, compute the expected sentence for
every edge whose `from` differs from its `to` using the same phrasing the description generator
produces, and confirm the rendered `desc` text contains each one. Confirm the `desc` names every
operator returned by `deriveCarriers`, and that it reports the feedback operator when
`getFeedbackOperator` returns one and reports its absence otherwise. Compute all of this from
`ALGORITHMS` at test time.

Structural counts across the dataset. For each algorithm, confirm the rendered DOM has exactly six
elements carrying an operator-id data attribute, that the number of modulation-class edge paths
equals the count of dataset edges where `from` differs from `to`, that the number of feedback-class
edge paths equals 1 when a feedback operator exists and 0 otherwise, and that the number of
output-bus stem paths equals the `deriveCarriers` length.

Role encoding across the dataset. For each algorithm and each operator group, confirm the
`data-role` attribute equals the role the derivation helper reports, and that the group's child
shape elements match that role — the carrier shape for carriers, the modulator shape for
modulators — using the same element expectations Plan 01's fixture spec encodes. No assertion in
this group may read a rendered color, fill or stroke value; the point is that the encoding survives
without color.

Id uniqueness across the dataset. For each algorithm, confirm the SVG title element id, the
description element id and the arrow marker id each contain that algorithm's id, and that every
`marker-end` reference in the rendered fragment points at that algorithm's own marker id. Then
confirm across the full run that the 32 title ids are pairwise distinct and the 32 marker ids are
pairwise distinct.

If the full sweep pushes the suite past the 10 second feedback budget recorded in
`04-VALIDATION.md`, reduce cost by reusing one fixture and resetting its input per id rather than
creating 32 fixtures — do not reduce coverage below all 32 algorithms.
  </action>

  <name>Task 2: Human verification — 32-diagram legibility, keyboard journey, screen-reader spot check</name>

  <what-built>
The full Phase 4 feature: a grouped 32-item browse view at `/algorithms`, a per-algorithm detail
route at `/algorithms/:id` with previous/next stepping and an explanatory not-found state, and an
accessible SVG routing diagram driven entirely by the canonical dataset plus 32 hand-authored layout
records.

Everything mechanically checkable is already green: all 32 layouts satisfy the grid, downward-flow,
carrier-row, clearance and bounds invariants; all 32 render with correct node, edge, feedback and
output-bus counts, a complete accessible description, non-color role encoding and unique ids; the
full rejected-address matrix lands on the not-found state.

Two things remain that no test can judge — whether each diagram actually *reads* cleanly, and how
the whole journey behaves for a keyboard and screen-reader user.
  </what-built>

  <how-to-verify>
Start the app with `npm start` and work through these four passes.

1. Layout legibility — all 32, not a sample. Open `/algorithms/1`, then use the next link to step
   through to `/algorithms/32`. For each diagram check: no two operator nodes or their numbers
   overlap; no modulation arrow passes visually through an unrelated node; the flow reads
   top-to-bottom with carriers along the bottom feeding the output bus; the feedback loop is
   obviously a loop returning into its own node and is visibly drawn differently from the straight
   modulation arrows. Note any algorithm id that needs a coordinate nudge.

2. Non-color encoding. On a diagram with both roles present (`/algorithms/1` is a good one), confirm
   carriers and modulators are told apart by their shape alone. Then force a monochrome view — the
   browser's grayscale rendering emulation in devtools, or the operating system's grayscale
   accessibility filter — and confirm the distinction still holds with no color at all. Do the same
   for the feedback path versus the modulation arrows.

3. Keyboard only. Put the mouse away. From `/algorithms`, tab to an algorithm card and activate it.
   On the detail page, tab to an operator node and activate it with Enter, then with Space; confirm
   the node highlights and its connected edges highlight, and that activating it again clears the
   selection. Confirm the focus ring is clearly visible on every stop. Tab to the next link and step
   to the following algorithm. Confirm no keyboard trap anywhere.

4. Screen reader spot check. With VoiceOver on macOS (Cmd+F5), navigate onto the diagram on
   `/algorithms/1`. Confirm the full routing description is announced — every modulation edge, the
   carrier list, the feedback operator — and not just a bare label. Then select an operator and
   confirm the selection is announced. Operator controls must be discoverable and labelled (Plan 01
   removes `role="img"` so `role="button"` nodes stay in the AT tree, or equivalent labelled controls
   outside the SVG). Record what you actually heard — this pass is blocking and is not deferred to
   HARDEN-01/Phase 13.

Also open `/algorithms/19` and confirm its historical-review note is visible both on the browse card
and on the detail page.

Report back: approved, or a list of algorithm ids needing a layout nudge plus anything the keyboard
or screen-reader passes surfaced. Layout nudges are edits to `ALGORITHM_LAYOUTS` records that must
keep every Plan 02 invariant green — re-run `npm test` after any adjustment.
  </how-to-verify>

  <resume-signal>Type "approved", or list the algorithm ids needing layout adjustment and describe any keyboard or screen-reader issues found.</resume-signal>
